# DocNori — แม่แบบเอกสาร

สถานะ: ข้อกำหนดผลิตภัณฑ์ได้รับการยืนยันในบทสนทนา; แบบระบบด้านล่างเสนอเพื่อทบทวนก่อนวางแผนลงมือทำ

## เป้าหมายและขอบเขตที่ตกลงกัน

สร้างแม่แบบ PDF ครั้งเดียว แล้วกรอกแบบฟอร์มเพื่อออกเอกสารหลายครั้ง เช่น สัญญาจ้าง หนังสือรับรอง และแบบฟอร์มตำแหน่งคงที่

- พื้นที่สมาชิกแยกจากเครื่องมือสาธารณะ ชื่อเมนู “พื้นที่ของฉัน” ภายในมี “แม่แบบเอกสาร”
- รองรับ Google และอีเมล/รหัสผ่าน พร้อมยืนยันอีเมลและลืมรหัสผ่าน
- เก็บเฉพาะแม่แบบและการตั้งค่าช่องในบัญชี ไม่เก็บข้อมูลที่กรอกหรือ PDF ผลลัพธ์อัตโนมัติ
- เจ้าของบัญชีเข้าถึงแม่แบบของตนเองเท่านั้น ไม่มีทีม ลิงก์สาธารณะ หรือสิทธิ์ร่วมแก้ไข
- รุ่นแรกใช้ตำแหน่งคงที่ ไม่มีตารางเพิ่มแถว/ขยายหน้าอัตโนมัติ นำเข้า Excel หรือส่งเซ็นเป็นชุด

## กฎสำคัญสี่ข้อ

1. ข้อความล้น: ไม่ตัดหรือย่อขนาดอัตโนมัติ แสดงข้อผิดพลาดใต้ช่องและกรอบแดงบนตัวอย่าง ผู้สร้างเลือกได้ว่าช่องใดอนุญาตหลายบรรทัด ต้องแก้ข้อความล้นก่อนดาวน์โหลด
2. ค่าเริ่มต้น: ผู้สร้างตั้งข้อมูลประจำ เช่น ชื่อบริษัทได้ ช่องที่ไม่ตั้งค่าเริ่มต้นเริ่มว่างทุกครั้ง ไม่จำข้อมูลผู้กรอกครั้งก่อน
3. การบันทึก: มีปุ่ม “บันทึกแม่แบบ” การกรอกใช้ฉบับที่บันทึกแล้วและไม่เปลี่ยนแม่แบบ หากมีการแก้พร้อมกันต้องแจ้งความขัดแย้ง ไม่เขียนทับเงียบ ๆ
4. ความเป็นส่วนตัว: แจ้งตรงหน้าอัปโหลดว่าเก็บแม่แบบในบัญชีเพื่อใช้ซ้ำ เจ้าของลบได้เอง ตรวจสิทธิ์ที่ API ทุกครั้ง

## หน้าจอและเส้นทาง

- `/templates`: หน้าสาธารณะอธิบายประโยชน์ พร้อมตัวอย่างและปุ่มเริ่มใช้งาน ไม่บังคับล็อกอินเครื่องมือ PDF เดิม
- `/account/login`, `/account/register`: Google และอีเมล/รหัสผ่าน; ยืนยันอีเมลและลืมรหัสผ่านเป็น flow แยก
- `/workspace/templates`: รายการแม่แบบของฉัน ค้นหาตามชื่อ ปุ่มหลัก “สร้างแม่แบบ”; แต่ละรายการมี “กรอกข้อมูล” และเมนูแก้ไข/ทำสำเนา/ลบ
- `/workspace/templates/new`: ชื่อแม่แบบ เลือก PDF และข้อความแจ้งการจัดเก็บ
- `/workspace/templates/{id}/edit`: ซ้ายรูปย่อหน้า กลางเอกสาร ขวาตั้งค่าช่อง ปุ่มบันทึกชัดเจน พร้อมสถานะมีการเปลี่ยนแปลง
- `/workspace/templates/{id}/fill`: แบบฟอร์มซ้าย ตัวอย่างขวา บนมือถือสลับ “กรอกข้อมูล / ดูตัวอย่าง”; ปุ่มดาวน์โหลดและเริ่มฉบับใหม่

ใช้สี ฟอนต์ ไอคอน ปุ่ม dropdown และ modal ร่วมกับ DocNori เดิม ไม่ใช้ browser confirm สำหรับการเปลี่ยนหน้าในเว็บ ส่วนรีเฟรช/ปิดแท็บยังเป็นคำเตือนของเบราว์เซอร์

## ช่องข้อมูลและตำแหน่ง

แยก Field (ข้อมูลหนึ่งค่า) ออกจาก Placement (ตำแหน่งที่แสดงข้อมูล)

- Field: id คงที่, ชื่อที่ผู้ใช้เห็น, ชนิดข้อความ/วันที่/ตัวเลข, บังคับกรอก, ค่าเริ่มต้น, ลำดับในฟอร์ม
- Placement: id, fieldId, หน้า, x/y/width/height ในพิกัด PDF, ฟอนต์/ขนาด/สี/การจัดแนว, อนุญาตหลายบรรทัด
- วางช่องแล้วเลือก “สร้างข้อมูลใหม่” หรือ “ใช้ข้อมูลเดิม” ไม่เชื่อมช่องอัตโนมัติจากชื่อที่ตรงกัน
- กรอก Field เดียวแล้วอัปเดตทุก Placement; แต่ละตำแหน่งต้องผ่านตรวจความพอดี
- ค่าเริ่มต้นอาจว่าง แม้เป็นช่องบังคับ; ผู้กรอกต้องเติมก่อนดาวน์โหลด
- วันที่เก็บเป็นค่าปฏิทินมาตรฐานและจัดรูปแบบไทยในเอกสาร ตัวเลขต้องไม่ถูกแปลงเป็นเลขทศนิยมโดยไม่ตั้งใจ; รหัส/เลขบัตรให้ใช้ชนิดข้อความ
- ตัววัดข้อความและตัวส่งออกต้องใช้ฟอนต์และกฎจัดบรรทัดเดียวกัน รองรับสระ/วรรณยุกต์ไทย และหน้า PDF ที่หมุนหรือมี CropBox

## การทำงานของแม่แบบ

ไฟล์ต้นฉบับไม่ถูกเขียนทับ การบันทึกสร้าง revision ใหม่ของคำจำกัดความช่อง และเปลี่ยน current revision แบบ atomic หน้ากรอกอ้าง revision ที่เปิดอยู่ ไม่เปลี่ยนกลางงานเมื่อแม่แบบถูกแก้ในอีกแท็บ

ทำสำเนาสร้างแม่แบบใหม่พร้อม Field/Placement ids ใหม่ การลบต้องยืนยันชื่อแม่แบบแล้วปิดการเข้าถึงทันที งานที่ดาวน์โหลดไปแล้วเรียกคืนไม่ได้ หน้าที่โหลดข้อมูลไปก่อนลบอาจยังมีข้อมูลในหน่วยความจำ จึงไม่รับรองการลบจากอุปกรณ์อื่นทันที

เสนอใช้ขนาดเอกสารตาม editor เดิม 25 MB / 100 หน้า; กำหนดโควตาจำนวนแม่แบบ/พื้นที่ต่อบัญชีเป็น configuration ก่อนเปิดสาธารณะและแสดงข้อจำกัดจริงบน UI

## ระบบสมาชิก

เสนอใช้ระบบมาตรฐานของ ASP.NET Core สำหรับบัญชีและ authentication cookie แบบ HttpOnly/Secure พร้อม CSRF protection แทนเก็บ bearer token ใน localStorage

- ยืนยันอีเมลก่อนอัปโหลดแม่แบบ; ลิงก์ยืนยันและรีเซ็ตรหัสมีอายุและใช้ตามกฎของระบบสมาชิก
- Google ใช้ OAuth ฝั่ง server พร้อมตรวจ state/correlation และ redirect ที่อนุญาต
- ไม่เชื่อมบัญชีโดยดูอีเมลตรงกันเพียงอย่างเดียว ผู้ใช้ต้องยืนยันบัญชีเดิมก่อนเพิ่ม Google
- ทุก template query ผูก authenticated user id จาก session ไม่เชื่อ ownerId ที่ส่งจาก client
- จำกัดความถี่ login/register/reset; ข้อความลืมรหัสผ่านไม่เปิดเผยว่ามีบัญชีหรือไม่
- หน้า account/workspace และ API ไม่ติดโฆษณาหรือสคริปต์ติดตาม; noindex และ no-store สำหรับข้อมูลส่วนตัว

## โครงสร้างที่เสนอให้เข้ากับระบบปัจจุบัน

Blazor Web App เดิม: public landing เป็น SSR; editor และ preview ใช้ WebAssembly/JavaScript เดิม; ASP.NET Core Host รับผิดชอบบัญชี สิทธิ์ และการเก็บแม่แบบ

จัดโฟลเดอร์ตาม feature: Accounts, DocumentTemplates, TemplateDesigner, TemplateFill แยกกฎ Field/Placement/Revision ออกจาก endpoint และ storage adapter ไม่แยก microservice ในรุ่นแรก

PostgreSQL บน Docker Compose เก็บข้อมูลบัญชี metadata revisions fields/placements ตามรูปแบบที่ version ได้ เก็บ PDF หลัง interface `ITemplateFileStore`: รุ่นแรก private persistent volume ที่อยู่นอก wwwroot และดาวน์โหลดผ่าน API ที่ตรวจเจ้าของ; อนาคตเปลี่ยนเป็น private object storage ได้โดยไม่เปลี่ยน editor

การอัปโหลดเป็น staged file ก่อนตรวจชนิด/ขนาด/จำนวนหน้าและบันทึก transaction; มี cleanup orphan files งานลบต้องจัดการทั้ง metadata และ binary แบบ retry ได้ ไม่รื้อหรือรีเซ็ตฐานข้อมูล/แอปอื่นบน VPS

การกรอกและสร้าง PDF ทำบนเครื่องผู้ใช้โดยรับไฟล์แม่แบบหลังตรวจสิทธิ์ ไม่ส่งค่าที่กรอกกลับ API ไม่บันทึกค่าใน localStorage/IndexedDB และไม่ใส่ชื่อไฟล์หรือเนื้อหาลง telemetry

## ขอบเขตความเป็นส่วนตัวที่ต้องสื่อสาร

ระบบสมาชิกที่เก็บแม่แบบต่างจากเครื่องมือที่ไม่อัปโหลดไฟล์: หน้าแรกและหน้าความเป็นส่วนตัวต้องแยกคำอธิบายตามเครื่องมือ

ผู้ใช้ยืนยันให้รุ่นแรกเป็น private server storage ที่ควบคุมสิทธิ์ ไม่ใช่ end-to-end encryption จึงไม่กล่าวว่าผู้ให้บริการไม่มีความสามารถอ่านแม่แบบ หากต้องการเงื่อนไขนั้นต้องออกแบบ key recovery และการเปิดข้ามอุปกรณ์แยกก่อน implementation ผู้ใช้ยืนยันทางเลือกนี้แล้วก่อนเริ่ม implementation

ร่างค่าที่กรอกหายเมื่อปิด/รีเฟรช หน้า fill แจ้งให้ดาวน์โหลดก่อนออก บันทึกแม่แบบไม่ใช่บันทึกค่าที่กำลังกรอก การลบหมายถึงปิดเข้าถึงและลบจาก active storage; อายุสำเนาสำรองต้องกำหนดและแจ้งตามการตั้งค่าจริงก่อน launch

## ข้อผิดพลาดและความปลอดภัยของเอกสาร

- ไม่รองรับไฟล์เสียหรือเอกสารมีลายเซ็นดิจิทัลตามข้อจำกัด editor เดิม
- PDF เข้ารหัส: เสนอให้ผู้ใช้เปิดด้วยรหัสบนเครื่องก่อนสร้างแม่แบบ และแจ้งว่าแม่แบบที่เก็บไม่คงรหัส PDF เดิม; ต้องตรวจสิทธิ์แก้ไขเช่นเดียวกับ editor
- หากบันทึกล้มเหลวคงการแก้ไขในหน้าปัจจุบัน พร้อม retry และไม่แสดงสำเร็จลวง
- Session หมดอายุ: ห้ามอัปโหลดต่อแบบ anonymous; แจ้งให้ล็อกอินใหม่ก่อน retry และหลีกเลี่ยง redirect ที่ทำงานในหน้าปัจจุบันหายโดยไม่เตือน
- ป้องกัน IDOR, path traversal, filename injection, oversized payload และ schema ที่มีพิกัด/ชนิดข้อมูลผิด

## เกณฑ์ทดสอบก่อนเปิดใช้งาน

1. สมัคร/ยืนยันอีเมล/login/reset/Google linking และการหมดอายุ session
2. บัญชี A อ่าน แก้ ทำสำเนา หรือลบแม่แบบ B ไม่ได้ แม้เดา id ได้
3. ช่องข้อมูลเดียวใช้ซ้ำหลายหน้า; ค่าเริ่มต้นแยกจากค่าของเอกสารครั้งก่อน
4. ตรวจข้อความล้นภาษาไทย หลายบรรทัด วันที่ ตัวเลข และข้อความยาว ไม่มีข้อความขาดหายเงียบ ๆ
5. Preview และ PDF ผลลัพธ์ใช้ตำแหน่งเดียวกัน ทั้งหน้าหมุนและขนาดต่างกัน
6. การกรอกไม่เปลี่ยนแม่แบบ; revision conflict ไม่เขียนทับ; โหลดแม่แบบแล้วกรอกใหม่ไม่มีข้อมูลผู้ใช้ครั้งก่อน
7. Network/storage checks ยืนยันค่าที่กรอกไม่ถูกส่งหรือเก็บอัตโนมัติ
8. ลบ/ทำสำเนา/upload failure/cleanup/quota; keyboard/mobile/unsaved-work modal
9. ตรวจการสำรองและกู้คืนทั้ง PostgreSQL และไฟล์โดยคงการผูกเจ้าของ

## สิ่งที่ต้องเตรียมก่อน production

Google OAuth client และ callback URLs, ผู้ส่งอีเมลยืนยัน/รีเซ็ตรหัส, domain sender verification, secret storage, โควตา, แผนสำรองข้อมูลและอายุสำเนาสำรอง ไม่มีการส่ง credentials ลงแชต

## ทางเลือกที่พิจารณา

- แนะนำ: บัญชีและแม่แบบอยู่ใน Host เดิม สร้างผลลัพธ์บนเครื่องผู้ใช้ ลดการส่งข้อมูลเฉพาะบุคคลและใช้ editor เดิมต่อได้
- สร้าง PDF บน server: เหมาะกับ batch/API ในอนาคต แต่ต้องส่งค่าที่กรอกและเพิ่ม worker/retention รุ่นแรกยังไม่ต้องใช้
- เก็บทุกอย่างใน browser: ไม่ตรงความต้องการเก็บในบัญชีและเปิดข้ามอุปกรณ์
